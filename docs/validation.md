# 自动校验

```bash
py -3 tools/validate.py                      # 全部
py -3 tools/validate.py --only script/06     # 只查某些文件
py -3 tools/validate.py --changed-only       # 只查这次改动的
py -3 tools/validate.py --format github      # CI 用
```

**错误挡住合并，警告不挡。**

校验**不需要游戏文件**——原文和技术元数据都在仓库里，
所以 GitHub Actions 上能跑，你在没装游戏的机器上也能跑。

---

## 它检查什么

它不评价译得好不好，只管两件事：**会不会把游戏弄坏**，
以及**符不符合项目约定**。

### 会把游戏弄坏的（错误）

| 检查 | 后果 |
|---|---|
| `src` / `ctl` 与 `jp` 对不上 | 有人改了原文，或这一行来自别的游戏版本 |
| 同一个 id 出现在两个文件里 | `allow.csv` 之类只按 id 定位，会指错行 |
| 控制码丢失或被改 | 颜色标记串行，整段变色 |
| `<CR>` 变多 | 多出来的行可能超出文本框 |
| 花括号数量变了或不配对 | 术语词典失效 |
| 字节数超过 `max_bytes - 1` | 字段被截断，可能崩溃 |
| 出现字库里没有的字 | 显示成方块 |
| 出现控制字符 | 解析异常 |
| 同一个 id 出现两次 | 注入时行为不确定 |
| 文件有 BOM 或 CRLF | 注入时字节对不上 |

### 项目约定（错误）

| 检查 | 为什么 |
|---|---|
| 译文里残留假名 | 基本都是漏译 |
| 用了术语表里的禁止译法 | 人名必须前后一致 |
| 同一句原文在非对白里译成两样 | 菜单、道具必须统一 |
| `status` 和有没有译文对不上 | 进度统计会失真 |

### 只是提醒（警告）

| 检查 | 为什么不是错误 |
|---|---|
| `<CR>` 变少 | 中文更短，减少换行通常是对的 |
| 单行超过 24 个字 | 少数场合确实需要长行 |
| 同一句原文在对白里译成两样 | 不同角色、不同场景，本来就该不一样 |

## 字库清单

「这个字画不画得出来」查的是 [`data/charset.txt`](../data/charset.txt)。

它由 `py -3 tools/export_charset.py` 从**打好补丁的 exe 里那张字形表**导出——
必须以最终真正能画出来的字为准，不能用字体构建时的候选清单：
排不进图集、或源字体没有轮廓的字，是进不了最终字形表的，
两者相差近 300 个字。

**每次重建字体后都要重新导出一次。**

## 需要破例时

**不要去改检查。** 在 [`data/allow.csv`](../data/allow.csv) 里加一行：

```csv
id,check,reason
ui/ui/title/uil_title_confirm_user_name.xml#1155,kana,界面排版中的假名占位，属于界面结构而非可翻译文本
```

三点好处：

1. 破例范围精确到"某一行的某一项检查"，不会顺手放过别的
2. 必须写理由，**没写理由的那一行不生效**
3. 出现在 diff 里，和别的改动一样接受评审

现在的豁免都是真有道理的：假名输入键盘的五十音、
错误代码里当标识符用的假名、制作人员署名（あちわ）、
以及一句**内容就是在讨论怎么写日文「の」**的台词。

## 校验器自己也要被检验

```bash
py -3 tools/selftest_validate.py
```

一个什么都放行的检查器比没有检查器更糟，因为大家会不再去看。

所以 `selftest_validate.py` 为每条规则造一行故意写坏的数据，
确认相应的报错真的出现；同时造一行完全正确的，确认它不会误报。
现在一共 19 项，CI 每次都跑。

---

## CI

`.github/workflows/validate.yml` 在 PR 和推送时跑三个任务：

| 任务 | 做什么 |
|---|---|
| **仓库中不得含有游戏文件** | 扫 `.pak`/`.g1t`/`.psarc`/游戏 exe，发现就失败 |
| **校验** | 跑 `validate.py`，并在摘要里写出翻译进度 |
| **工具自检** | 编译检查、确认无游戏也能导入、跑 `selftest_validate.py` |

第一项是硬性的红线：仓库里永远不该出现游戏原始文件。
安装包的构建脚本 `build-installer.ps1` 也会在打包前再查一次。

## 涉及封包和 exe 的改动

这些改动一旦出错，表现往往是游戏直接崩溃或满屏乱码，
所以有两个额外的检查，**需要有游戏才能跑**：

```bash
py -3 tools/test_roundtrip.py
```

验证空改动重建出来的封包和原始封包**逐字节相同**。
这是注入逻辑没有副作用的证明。

```bash
py -3 tools/check_exe_text.py --archives
```

验证 exe 字符串的译文都能装下、都能在 exe 里精确定位，
并且检查这个字符串是不是也作为**完整字段**出现在游戏运行时
读取的数据里——如果是，引擎可能按名字查它，改了会失配。
